A https://docs.koog.ai/[Koog] `LLMClient` implementation for
https://gonka.ai[Gonka] — a decentralized, blockchain-based AI compute
network (Cosmos SDK L1 chain, native token GNK).

`koog-gonka` lets any Koog-based Kotlin project use Gonka as a regular LLM
provider, on equal footing with OpenAI, Anthropic, Google, Mistral, or
Ollama — through Koog's standard `LLMClient` abstraction.

== Status

Early development. No release yet.

== Authentication

Two auth modes are planned, both behind the same client interface:

* *API key via Gonka Broker* (first wave) — OpenAI-compatible endpoint,
  classic USD card billing, no wallet required.
* *Wallet-based direct chain access* (later wave) — secp256k1 request
  signing against the Gonka chain, no centralized broker layer.

== Publishing to Maven Central

[[publishing]]
`koog-gonka` publishes to Maven Central (only channel — no Homebrew, no other
distribution) via the
https://github.com/vanniktech/gradle-maven-publish-plugin[vanniktech maven-publish
plugin] and the `.github/workflows/release.yml` workflow, triggered by pushing a
`vX.Y.Z` tag.

=== Already done

* Sonatype Central Portal namespace `de.betchvaia` is verified (DNS TXT record at
  netcup) — no further namespace setup needed.
* `build.gradle.kts` (root) configures coordinates, POM metadata, and
  `publishToMavenCentral(automaticRelease = true)` for every `org.jetbrains.kotlin.jvm`
  subproject.
* `./gradlew publishToMavenLocal` works with no credentials — a safe way to verify the
  publication shape (POM, sources jar, empty javadoc jar) before touching real
  credentials.

=== Still needed (one-time, manual — not something an agent should do)

. *Sonatype user token*: on
  https://central.sonatype.com[central.sonatype.com], under the `de.betchvaia`
  namespace, generate a user token (not your login password). Two values come out of
  this: a username and a password.
. *GPG signing key*:
+
[source,bash]
----
gpg --quick-generate-key "koog-gonka Release <irakli@betchvaia.de>" rsa4096 sign 0
gpg --list-secret-keys --keyid-format=long
# note the key id, e.g. ABC1234567890DEF

gpg --armor --export-secret-keys ABC1234567890DEF > koog-gonka-signing-key.asc
gpg --keyserver keyserver.ubuntu.com --send-keys ABC1234567890DEF
----
. *GitHub Secrets* (repo Settings → Secrets and variables → Actions):
+
[cols="1,2"]
|===
| Secret | Value

| `SONATYPE_USERNAME` | Sonatype user-token username (step 1)
| `SONATYPE_PASSWORD` | Sonatype user-token password (step 1)
| `GPG_SIGNING_KEY` | Contents of `koog-gonka-signing-key.asc` (full ASCII-armored block, step 2)
| `GPG_PASSPHRASE` | Passphrase for the GPG key (empty string if none)
|===

Once those four secrets exist, pushing a `vX.Y.Z` tag runs the release workflow
end-to-end: build & test, publish to Maven Central (skipped idempotently if that
version is already live), create the GitHub Release.

A maintainer can also publish a real (non-SNAPSHOT) version from a local machine
without CI, by setting the same four values as Gradle properties
(`~/.gradle/gradle.properties` or `-P`/`ORG_GRADLE_PROJECT_*` env vars, matching the
names `mavenCentralUsername` / `mavenCentralPassword` / `signingInMemoryKey` /
`signingInMemoryKeyPassword`) and running `./gradlew publishToMavenCentral`.

== Maintenance

=== Keeping in sync with Koog

`koog-gonka`'s Kotlin and JDK versions are deliberately pinned to match Koog's
own build *exactly*, not just "compatible" — see <<why-exact-versions,rationale>>
below. Whenever the `koog` version in `gradle/libs.versions.toml` is bumped:

. Check Koog's own `gradle/libs.versions.toml` and
  `convention-plugin-ai/src/main/kotlin/ai.kotlin.configuration.gradle.kts`
  (in https://github.com/JetBrains/koog[JetBrains/koog], on the matching release
  tag) for its `kotlin`, `jdkVersion`, and `jvmTarget` values.
. Update `kotlin` in `gradle/libs.versions.toml` to match.
. Update `jvmToolchain(...)` in `koog-gonka/build.gradle.kts` to match Koog's
  JVM target / JDK toolchain.
. Check whether Koog's `ktor`, `kotlinx-coroutines`, and `kotlinx-serialization`
  versions have also moved, and whether `koog-gonka`'s own pins should follow —
  `GonkaLLMClient` exposes `ktor-client-core` types on its public constructor, so
  a stale pin there is the most likely of the three to actually break something.
. Run `./gradlew clean check`, and verify with `--info` that compilation actually
  uses the intended JDK (`... --info 2>&1 | grep -i jdkHome`).
. Update the Kotlin/JDK badges at the top of this README.

[[why-exact-versions]]
*Rationale:* `GonkaLLMClient` extends Koog's `@ApiStatus.Experimental`-marked
internals (`AbstractOpenAILLMClient`, `KtorKoogHttpClient`) rather than only
stable public API. Kotlin's forward-compatibility guarantees make a
newer-Kotlin-than-Koog setup work in practice (verified once, see git history),
but exact version parity removes that residual risk entirely for code sitting
this close to Koog's unstable internals.
