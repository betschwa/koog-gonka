A https://docs.koog.ai/[Koog] `LLMClient` implementation for
https://gonka.ai[Gonka] — a decentralized, blockchain-based AI compute
network (Cosmos SDK L1 chain, native token GNK).

`koog-gonka` lets any Koog-based Kotlin project use Gonka as a regular LLM
provider, on equal footing with OpenAI, Anthropic, Google, Mistral, or
Ollama — through Koog's standard `LLMClient` abstraction.

== Status

Released. `v0.1.0` is on Maven Central — `GonkaLLMClient` (Broker API-key auth) is
fully functional; `GonkaAuth.Wallet` (secp256k1 signing primitives) is implemented
but its dispatch path is deliberately stubbed, see <<authentication,Authentication>>.

[[authentication]]
== Authentication

Two auth modes, both behind the same `GonkaAuth` interface:

* *API key via Gonka Broker* (`GonkaAuth.ApiKey`) — OpenAI-compatible endpoint,
  classic USD card billing, no wallet required. `GonkaLLMClient` fully implements
  dispatch against it.
* *Wallet-based direct chain access* (`GonkaAuth.Wallet`) — secp256k1 identity and
  request-signing primitives are implemented and tested, ported directly from
  Gonka's own Go source. `GonkaWalletLLMClient`'s actual dispatch is deliberately
  NOT implemented yet: Gonka's own `devshard/bridge` chain-bridge interface is
  marked "Phase 1: interface only, no implementation" upstream, and broker-less
  wallet signing does not work end-to-end on the network today (see that class's
  KDoc for citations). Calling `execute`/`executeStreaming`/`moderate` on it throws
  `UnsupportedOperationException` with an explanation.

== Publishing to Maven Central

[[publishing]]
`koog-gonka` publishes to Maven Central (only channel — no Homebrew, no other
distribution) via the
https://github.com/vanniktech/gradle-maven-publish-plugin[vanniktech maven-publish
plugin] and the `.github/workflows/release.yml` workflow, triggered by pushing a
`vX.Y.Z` tag.

=== One-time setup (completed 2026-08-20)

* Sonatype Central Portal namespace `de.betchvaia` verified (DNS TXT record at
  netcup).
* `build.gradle.kts` (root) configures coordinates, POM metadata, and
  `publishToMavenCentral(automaticRelease = true)` for every `org.jetbrains.kotlin.jvm`
  subproject.
* Sonatype user token, GPG signing key, and the four GitHub Secrets below are set.
  `.github/workflows/release.yml` runs the `publish` job with `permissions: contents:
  write` at the job level (the repo's default workflow permissions are read-only,
  which broke GitHub Release creation on the first attempt — see git history for
  `v0.1.0`).

[cols="1,2"]
|===
| Secret | Value

| `SONATYPE_USERNAME` | Sonatype user-token username
| `SONATYPE_PASSWORD` | Sonatype user-token password
| `GPG_SIGNING_KEY` | ASCII-armored GPG private key (`gpg --armor --export-secret-keys <key-id>`)
| `GPG_PASSPHRASE` | Passphrase for the GPG key (empty string if none)
|===

=== Cutting a release

. Bump `version` in `build.gradle.kts` (root) to a non-SNAPSHOT version.
. Commit and push to `master`.
. `git tag -a vX.Y.Z -m "..."` and `git push origin vX.Y.Z`.

The release workflow then runs end-to-end: build & test, publish to Maven Central
(skipped idempotently if that version is already live — Central is immutable), create
the GitHub Release. CDN propagation to `repo1.maven.org` after a successful
`publishToMavenCentral` can take anywhere from a few minutes to ~30 minutes for a new
version.

A maintainer can also publish from a local machine without CI, by setting the same
four values as Gradle properties (`~/.gradle/gradle.properties` or
`-P`/`ORG_GRADLE_PROJECT_*` env vars, matching the names `mavenCentralUsername` /
`mavenCentralPassword` / `signingInMemoryKey` / `signingInMemoryKeyPassword`) and
running `./gradlew publishToMavenCentral`.

== Maintenance

=== Keeping in sync with Koog

`koog-gonka`'s Kotlin and JDK versions are deliberately pinned to match Koog's
own build *exactly*, not just "compatible" — see <<why-exact-versions,rationale>>
below. Whenever the `koog` version in `gradle/libs.versions.toml` is bumped:

. Check Koog's own `gradle/libs.versions.toml` and
  `convention-plugin-ai/src/main/kotlin/ai.kotlin.configuration.gradle.kts`
  (in https://github.com/JetBrains/koog[JetBrains/koog], on the matching release
  tag) for its `kotlin`, `jdkVersion`, and `jvmTarget` values.
. Update `kotlin` in `gradle/libs.versions.toml` to match.
. Update `jvmToolchain(...)` in `koog-gonka/build.gradle.kts` to match Koog's
  JVM target / JDK toolchain.
. Check whether Koog's `ktor`, `kotlinx-coroutines`, and `kotlinx-serialization`
  versions have also moved, and whether `koog-gonka`'s own pins should follow —
  `GonkaLLMClient` exposes `ktor-client-core` types on its public constructor, so
  a stale pin there is the most likely of the three to actually break something.
. Run `./gradlew clean check`, and verify with `--info` that compilation actually
  uses the intended JDK (`... --info 2>&1 | grep -i jdkHome`).
. Update the Kotlin/JDK badges at the top of this README.

[[why-exact-versions]]
*Rationale:* `GonkaLLMClient` extends Koog's `@ApiStatus.Experimental`-marked
internals (`AbstractOpenAILLMClient`, `KtorKoogHttpClient`) rather than only
stable public API. Kotlin's forward-compatibility guarantees make a
newer-Kotlin-than-Koog setup work in practice (verified once, see git history),
but exact version parity removes that residual risk entirely for code sitting
this close to Koog's unstable internals.
